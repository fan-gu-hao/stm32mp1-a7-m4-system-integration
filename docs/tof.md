# 測距介面與功能驗證

## 資源分配

感測器透過 PA11／PA12 的 I²C5 連接 M4。

Linux 裝置樹停用一般 I²C5 裝置節點，
由遠端處理器資源管理機制保留該周邊與接腳給 M4。
M4 使用硬體信號量 HSEM 0 保護 GPIO 配置操作。

此版本讀取到的 I²C35 核心時鐘為 64 MHz。
I²C 時序設定為 `0x70A22727`；沒有以示波器量測實際 SCL 頻率。

VL53L0X 的 7 位元位址為 `0x29`，
移植層交給 STM32 HAL 的位址為左移一次後的 `0x52`。

## 通訊分工

| 通道 | A7 傳送 | M4 傳送 |
|---|---|---|
| `/dev/ttyRPMSG0` | `READY` | 量測資料 |
| `/dev/ttyRPMSG1` | 控制或查詢命令 | 確認回覆、狀態或診斷結果 |

文字訊息以換行分隔。
A7 接收端會重新組合資料，不假設一次 read 就對應完整一行。

## 命令

| 命令 | 用途 |
|---|---|
| `TOF,START` | 開始週期測距 |
| `TOF,STOP` | 停止後續量測 |
| `TOF,STATUS` | 查詢執行狀態、序號與傳送丟棄計數 |
| `TOF,PROBE` | 停止狀態下檢查匯流排與感測器識別 |
| `TOF,RANGE` | 停止狀態下執行一次量測 |

已取得的回覆範例：

```text
TOF,ACK,START,PERIOD_MS=100,FW=TOF_STREAM_V1
TOF,DATA,SEQ=30,MS=4083,TX_DROP=0,OK,MM=181,RANGE_STATUS=0,FW=TOF_STREAM_V1
TOF,ACK,STOP,FW=TOF_STREAM_V1
TOF,STATUS,RUN=0,SEQ=30,TX_DROP=0,FW=TOF_STREAM_V1
```

| 欄位 | 定義 |
|---|---|
| SEQ | M4 的量測嘗試序號；停止及再開始不會將它歸零 |
| MS | M4 進入本次量測呼叫時的系統毫秒計數 |
| TX_DROP | M4 端待傳資料因被替換或丟棄而增加的計數 |
| MM | 有效量測的距離，單位毫米 |
| RANGE_STATUS | 原廠 API 的量測狀態 |
| FW | 應用層韌體版本識別 |

`MS` 不是光學量測完成時間；`TX_DROP` 也不是完整資料路徑的遺失率。

M4 以非阻塞傳送避免無限等待傳送緩衝區。
圖形程式另以序號檢查接收資料的連續性。

## 已完成的功能驗證

以下根據 2026-09-23 的板端輸出與實際操作整理。

| 檢查 | 已觀察到的結果 |
|---|---|
| 感測器識別 | ID `0xEEAA`、REV `0x10` |
| 單次量測 | 回傳有效距離，移動手的位置時數值改變 |
| 串流量測 | 連續取得 SEQ 1 至 30，該次 TX_DROP 均為 0 |
| 目標週期 | 第 2 筆之後，該次紀錄中的相鄰 MS 間隔為 100 ms |
| 停止命令 | 收到 STOP 確認；相隔一秒的兩次查詢均維持 RUN=0、SEQ=30 |
| 圖形介面 | 視窗出現，START／STOP 正常，距離隨手的位置變化 |
| 重新開機 | M4 與圖形服務自動啟動，視窗先保持停止狀態 |

這些是功能驗收紀錄，沒有進行距離精度校準或長時間時序保證測試。

## 啟動問題與修正

初期在感測器軟體重置後，第一筆識別暫存器讀取失敗：

```text
STAGE=RESET
STEP=WAIT_ID
REG=0xC0
API=-20
HAL=1
I2C=0x00000020
```

診斷版本保留第一筆 I²C 錯誤及當時的重置階段。
在解除軟體重置後，增加 5 ms 等待，再讀取型號識別，
後續感測器初始化與單次量測成功。

## 本版本的行為界線

- M4 採裸機主迴圈，沒有使用即時作業系統（RTOS）。
- 100 ms 是目標排程週期；首次初始化或錯誤處理可能造成較長間隔。
- 單次量測 API 會阻塞，因此 STOP 需等目前的量測呼叫返回後處理。
- 感測器 API 錯誤會停止串流，可透過 START 再次嘗試。
- 圖形程式使用固定長度歷史資料，顯示最近 20 秒曲線。
- 此版本提供固定週期測距與 START／STOP，尚未實作取樣率選擇、門檻控制或 CSV 紀錄。
- 原廠核心、HAL、OpenAMP 與感測器 API 的實作仍由各自上游專案提供。
